## Video room: lighter for long calls (hang after 3+ hours with other apps open)
What kept the computer busy on every frame for the whole call, on top of the video itself:
- the glowing frame round the video turned non-stop (a conic-gradient animation redrawn by the processor every frame),
- three half-screen blurred background lights moved non-stop behind the video,
- a film-grain layer was blended over the whole screen,
- the "who is talking" sound bars changed height (page re-layout every frame while anyone talks).

Changes (`wwwroot/css/room-light.css`, new, loaded by `Views/Meetings/Room.cshtml`):
- background lights and the video frame stay still (same look; the frame still brightens while someone talks),
- film grain removed (it was at 6 %, hardly visible),
- sound bars use a transform (graphics card) instead of changing height,
- when the call tab or window is hidden or minimised, every decoration pauses.
`wwwroot/js/room.js`: sets that pause, and turns on Jitsi's adaptive mode (`videoQuality.enableAdaptiveMode`) so that
when the computer is overloaded Jitsi lowers the video instead of letting the computer hang.

## Video room: big calls get lighter by themselves (10+ people)
`wwwroot/js/room.js`
- **Only recent speakers' video** (Jitsi "last N", `lastNLimits`): from 10 people everyone receives the video of the
  6 latest speakers; from 30 people 5; from 60 people 4. Others show as picture / initials. Under 10: everyone's video, as before.
- **720p limit**: when the 10th person joins, video is limited to 720p (`setVideoQuality`), with a short note in the room.
  It goes back to the plan's quality (e.g. 1080p) when the call is down to 8 people. Plans at 720p or lower: no change.
- Both work with JaaS and with your own Jitsi server. On your own server, if "last N" doesn't apply, allow
  `channelLastN` and `lastNLimits` in the server's config whitelist (or set them in its config.js).

## Ready for several web servers (nothing changes until you fill in new settings)
With no new settings the app runs exactly as today on one server (shared hosting, JaaS, Azure SQL).
When you add servers later it is **settings only** (see the server setup guide, section 6).

New packages (restored automatically on build): StackExchange.Redis 2.8.16 and AWSSDK.S3 (ServiceLibrary),
Microsoft.AspNetCore.SignalR.StackExchangeRedis and Microsoft.AspNetCore.DataProtection.StackExchangeRedis 10.0.15 (Web).
They are only used when the settings below are filled in.

Optional settings (appsettings.json; leave them out to keep today's behaviour):
```json
"Redis":   { "Connection": "<ip>:6379,password=<pw>,abortConnect=false", "KeyPrefix": "sn:" },
"App":     { "RunBackgroundJobs": true },          // false on every web server except one
"Storage": { "Kind": "Local" }                     // or "S3" with "S3": { ServiceUrl, Bucket, AccessKey, SecretKey, Region, ForcePathStyle }
```

What changed:
- `ServiceLibrary/Infrastructure/Cluster.cs` (new): the Redis connection (if set), this server's id, and a shared "once per window" check.
- `ServiceLibrary/Infrastructure/Trackers.cs`: who is online / status / who is in which call is kept in Redis when it is set
  (same methods, so none of the 84 callers changed); in memory otherwise, exactly as before.
- `ServiceLibrary/Infrastructure/S3FileStorage.cs` (new) + `FileStorage.cs`: `Storage:Kind = "S3"` stores uploads in any S3-style
  store (MinIO, Cloudflare R2, AWS, Wasabi), same file paths, video seeking still works.
- `ServiceLibrary/ServiceRegistration.cs`: registers the above.
- `Web/Program.cs`: with Redis set, live updates (SignalR) and login keys go through Redis; `App:RunBackgroundJobs` switch.
- `Web/Infrastructure/ClusterHeartbeat.cs` (new): with Redis set, each server says "alive" every 20 s; if one stops, another marks
  its people offline and out of their calls within about a minute.
- `Web/Hubs/ChatHub.cs`, `Web/Controllers/ChatController.cs`: meeting ringing (2 min), "meeting started" emails (3 h) and Ping (15 s)
  use the shared check, so 2 servers never ring or email twice.
- Both `.csproj` files: the packages above.

Tested here: the whole solution builds (.NET 10, 0 errors); online / status / in-call tracking passes 42 checks both in memory
and with two app copies sharing one Redis; S3 storage tested for save, read, seek, delete. Not tested here: the full app
against your Azure database (please run it once locally before uploading).

Note (already there before today): MailKit 4.8.0 has known security advisories; updating MailKit to the latest 4.x is advised.
